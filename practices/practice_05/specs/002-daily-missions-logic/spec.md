# Feature Specification: Ежедневные задания — логика

**Feature Branch**: `002-daily-missions-logic`

**Created**: 2026-10-19

**Status**: Draft (согласована с общим контрактом)

**Contract**: [`specs/daily-missions-contract.md`](../daily-missions-contract.md) — общий контракт
UI ↔ логика, v1.1, принят владельцем продукта 2026-10-19. При расхождении спеки и контракта прав
контракт; изменение контракта — только решением человека с обновлением обеих спек.

**Input**: User description: "Ежедневные задания. Каждый день игроку выдаются 3 задания (например: собрать монеты, сделать идеальные переключения передач, проехать дистанцию). Прогресс копится по всем заездам за день. За выполненное задание полагается награда монетами в кошелёк гаража, награду нужно забрать. На следующий день задания новые."

**Зона спеки**: только правила и данные (что такое задание, как выбирается набор дня, как считается
прогресс, когда задание выполнено, как начисляется награда, смена дня, ошибки, хранение, интерфейс
логики для остальной игры). Экраны, кнопки, тексты и их состояния описывает UI-спека
(`specs/001-daily-missions-ui`); стыковка — по общему контракту (конституция, принцип VI).

## Clarifications

### Session 2026-10-19

- Q: Что происходит с выполненным, но не забранным заданием при смене дня? → A: Награда
  автоматически зачисляется в кошелёк гаража при смене дня; логика возвращает сумму автозачисления,
  чтобы игра могла об этом сообщить.
- Q: Пул видов заданий — только три вида из примера или шире с выбором 3 из пула? → A: Сейчас ровно
  3 вида (монеты, идеальные переключения, дистанция), каждый день по одному заданию каждого вида,
  меняются цели и награды; модель данных допускает расширение пула видов позже.
- Q: Награда фиксирована по сложности или есть бонус за все три задания дня? → A: Фиксированные
  20/40/60 монет по сложности, без бонуса за все три; конкретные числа целей и наград остаются
  допущением и будут проверены отдельно.
- Q: Как спека логики стыкуется с UI-спекой (согласование контракта 2026-10-19)? → A: По общему
  контракту `specs/daily-missions-contract.md`: id задания `"<день>:<вид>"`, поле `level`, поле
  `seen` в состоянии дня; новые операции `nextDayStart`, `previewCompleted`, `markMissionsSeen`;
  учёт заезда возвращает `gains` и `dayChanged`, актуализация дня — `dayChanged`; получение
  награды не актуализирует день, а при вчерашнем id отказывает с `stale-day`; у всех ошибок логики
  поле `code`; цели уровней сложности пересчитаны по замеру симуляцией (60/150/300, 3/8/12,
  1000/3000/6000 м), награды 20/40/60 без изменений.
- Q: Какие решения приняты по вопросам команд после сверки спек с контрактом v1.0 (контракт v1.1,
  2026-10-19)? → A: `stale-day` — только если день в id раньше текущего дня; при часах, переведённых
  назад, награда за задание сохранённого набора выдаётся как обычно; неверный тип ввода —
  `TypeError`, неверное значение — `RangeError`, у обеих `code: "invalid-input"`; `parseMissions`
  оставляет действующим набор с днём позже текущего; UI вызывает `previewCompleted` только при
  `state.day === dayKey(now)`; текст `unknown-mission` остаётся «неизвестное задание: "<id>"» —
  он для логов, игроку UI показывает общий текст.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Набор заданий дня (Priority: P1)

Игрок открывает игру и получает три задания на сегодня: «собрать N монет», «сделать N идеальных
переключений», «проехать N метров» — у каждого цель, уровень сложности, прогресс (в начале дня 0) и
награда. В течение дня набор не меняется, сколько бы раз игрок ни перезапускал игру.

**Why this priority**: без набора дня нет ни прогресса, ни наград — это основа фичи.

**Independent Test**: запросить набор на заданную дату дважды (в том числе после «перезапуска» —
сохранения и чтения состояния) и убедиться, что это одни и те же 3 задания с прогрессом 0.

**Acceptance Scenarios**:

1. **Given** у игрока нет сохранённых заданий, **When** игра запрашивает задания на 2026-10-19,
   **Then** логика выдаёт состояние дня `2026-10-19` с `seen: false` и ровно 3 заданиями в порядке
   «монеты, идеальные переключения, дистанция» с id `2026-10-19:coins`, `2026-10-19:perfectShifts`,
   `2026-10-19:distance`; у каждого уровень 0–2, цель и награда из таблицы уровней, прогресс 0,
   награда не забрана.
2. **Given** набор на 2026-10-19 уже выдан и сохранён, **When** игра перезапущена в тот же день,
   **Then** выдаётся тот же набор (те же уровни, цели, награды) с сохранённым прогрессом.
3. **Given** две чистые установки в один и тот же день, **When** каждая получает набор, **Then**
   наборы совпадают (выбор зависит только от даты).

### User Story 2 — Прогресс копится по заездам за день (Priority: P1)

После каждого заезда его итоги (собранные монеты, идеальные переключения, пройденная дистанция)
прибавляются к прогрессу заданий текущего дня. Когда прогресс достигает цели, задание становится
выполненным. Во время заезда игра может узнать, какие задания эти итоги уже довели бы до цели, не
меняя состояние.

**Why this priority**: это и есть «игровая петля» заданий; без неё задания не выполнить.

**Independent Test**: подать в логику итоги нескольких заездов и проверить прогресс, прибавку по
каждому заданию и момент выполнения; проверить предпросмотр без изменения состояния.

**Acceptance Scenarios**:

1. **Given** задание «собрать 150 монет» с прогрессом 0, **When** закончен заезд с 57 монетами,
   **Then** прогресс 57 из 150, прибавка этого задания 57, задание не выполнено.
2. **Given** прогресс 120 из 150, **When** закончен заезд с 57 монетами, **Then** прогресс 150 из 150
   (не больше цели), прибавка 30, задание в списке выполненных этим заездом.
3. **Given** заезд закончился аварией или выходом в меню через паузу, **When** итоги учитываются,
   **Then** они прибавляются к заданиям ровно один раз — так же, как монеты этого заезда к кошельку.
4. **Given** задание уже выполнено, **When** закончен ещё один заезд, **Then** его прогресс и статус
   не меняются, прибавка 0, а остальные задания продолжают копить прогресс.
5. **Given** задание «проехать 3000 м», **When** заезды прошли 1234,6 м и 900,9 м, **Then** прогресс
   1234 + 900 = 2134 (каждый заезд учитывается целыми метрами, дробная часть отбрасывается).
6. **Given** задание «собрать 60 монет» с прогрессом 40, **When** во время заезда игра запрашивает
   предпросмотр с текущими итогами «25 монет», **Then** логика отвечает, что это задание было бы
   выполнено, а состояние заданий остаётся прежним (прогресс 40).
7. **Given** задание уже выполнено ранее, **When** запрошен предпросмотр с любыми итогами, **Then**
   этого задания нет в ответе (оно не «впервые» доводится до цели).

### User Story 3 — Забрать награду в кошелёк гаража (Priority: P1)

За выполненное задание игрок забирает награду: монеты добавляются в общий кошелёк гаража, задание
помечается как «награда получена». Забрать награду можно только один раз, только за выполненное
задание и только за задание сегодняшнего дня.

**Why this priority**: награда — смысл заданий для игрока; монеты тратятся на улучшения гаража.

**Independent Test**: выполнить задание, забрать награду, проверить кошелёк; проверить каждый вид
отказа и что при отказе ничего не меняется.

**Acceptance Scenarios**:

1. **Given** в кошельке 100 монет и выполнено задание с наградой 40, **When** игрок забирает награду,
   **Then** в кошельке 140 монет, задание отмечено «награда получена», логика возвращает награду 40.
2. **Given** награда за задание уже получена, **When** игрок снова пытается её забрать, **Then** отказ
   `already-claimed` «Награда за задание уже получена», кошелёк и задания не меняются.
3. **Given** задание выполнено на 37 из 60, **When** игрок пытается забрать награду, **Then** отказ
   `not-completed` «Задание ещё не выполнено: 37 из 60», кошелёк и задания не меняются.
4. **Given** сегодня 2026-10-19, **When** запрошено забрать награду за `2026-10-19:jumps` (такого
   задания в наборе нет), **Then** отказ `unknown-mission` «неизвестное задание: "2026-10-19:jumps"»
   (текст для логов), ничего не меняется.
5. **Given** состояние за 2026-10-19 с выполненным незабранным заданием, а сегодня уже 2026-10-20,
   **When** игрок пытается забрать награду `2026-10-19:coins`, **Then** отказ `stale-day`
   «Задания устарели — наступил новый день», состояние и кошелёк не меняются, автозачисления нет;
   последующая актуализация дня зачисляет эту награду автоматически (User Story 4).
6. **Given** в кошельке 100 монет, сохранён набор за 2026-10-19 с выполненным незабранным заданием
   `2026-10-19:coins` (награда 20), а часы устройства переведены назад на 2026-10-18, **When** игрок
   забирает эту награду, **Then** награда выдаётся как обычно: в кошельке 120 монет, задание
   отмечено «награда получена», отказа `stale-day` нет.

### User Story 4 — Новый день — новые задания (Priority: P2)

С наступлением следующего календарного дня прежний набор заменяется новым, прогресс начинается с нуля,
отметка «игрок видел задания» сбрасывается, а награды выполненных, но не забранных заданий прошлого
набора автоматически зачисляются в кошелёк. Игра может узнать, когда наступит следующий день.

**Why this priority**: ежедневное обновление удерживает игрока, но фича полезна и в пределах одного дня.

**Independent Test**: сохранить состояние за 19.10, актуализировать на 20.10 и проверить новый набор,
автозачисление и признак смены дня; актуализировать на 18.10 (часы назад) и проверить, что набор
не сбросился.

**Acceptance Scenarios**:

1. **Given** сохранён набор за 2026-10-19 с прогрессом и `seen: true`, **When** выполняется
   актуализация на 2026-10-20, **Then** выдаётся набор 2026-10-20 с прогрессом 0 и `seen: false`,
   признак смены дня — да.
2. **Given** сохранён набор за 2026-10-19, а часы устройства показывают 2026-10-18, **When**
   выполняется актуализация, **Then** остаётся набор 2026-10-19 с его прогрессом, автозачисление 0,
   признак смены дня — нет.
3. **Given** набор за 2026-10-19 и заезд закончился в 00:01 2026-10-20, **When** учитываются итоги,
   **Then** сначала происходит смена дня (с автозачислением), итоги заезда идут в набор 2026-10-20,
   логика сообщает о смене дня.
4. **Given** в кошельке 100 монет и за 2026-10-19 осталось выполненное, но не забранное задание
   с наградой 40, **When** выполняется актуализация на 2026-10-20, **Then** в кошельке 140 монет,
   автозачисление 40, набор 2026-10-20 с прогрессом 0.
5. **Given** за 2026-10-19 есть невыполненное задание (37 из 60) и задание с уже забранной наградой,
   **When** актуализация на 2026-10-20, **Then** автозачисление 0, кошелёк не меняется.
6. **Given** за 2026-10-19 выполнены и не забраны два задания (20 и 60), а игрок не заходил до
   2026-10-23, **When** актуализация на 2026-10-23, **Then** автозачисление 80 — ровно один раз,
   наборы пропущенных дней не создаются и ничего не начисляют.
7. **Given** момент 2026-10-19 15:30 по местному времени, **When** игра запрашивает начало следующего
   дня, **Then** логика возвращает момент 2026-10-20 00:00 по местному времени.

---

### User Story 5 — Отметка «игрок видел задания» (Priority: P3)

UI показывает отметку «Новые!», пока игрок в этот день не открыл экран заданий. Логика хранит
признак просмотра в состоянии дня и сбрасывает его в новый день.

**Why this priority**: удобство, а не правила заданий; без него фича работает.

**Independent Test**: отметить состояние просмотренным, проверить признак; сменить день — признак
сброшен.

**Acceptance Scenarios**:

1. **Given** состояние дня с `seen: false`, **When** игра отмечает задания просмотренными, **Then**
   возвращается состояние с `seen: true`, задания (прогресс, награды) не меняются, исходное состояние
   не изменено.
2. **Given** состояние с `seen: true`, **When** отмечено ещё раз, **Then** результат тот же
   (`seen: true`), ошибки нет.
3. **Given** `seen: true` за 2026-10-19, **When** актуализация на 2026-10-20, **Then** `seen: false`.

---

### User Story 6 — Сохранение между перезапусками и повреждённые данные (Priority: P2)

Прогресс, отметки о полученных наградах и признак просмотра переживают перезагрузку страницы.
Испорченное или недоступное хранилище не ломает игру и не трогает кошелёк гаража.

**Why this priority**: без сохранения прогресс «за день» теряется при перезапуске; без терпимого
разбора игра может упасть.

**Independent Test**: сохранить состояние, прочитать его; подать в разбор мусор и частично
испорченные данные и проверить результат.

**Acceptance Scenarios**:

1. **Given** прогресс 37 из 60 сохранён, **When** страница перезагружена в тот же день, **Then**
   прогресс 37 из 60.
2. **Given** в хранилище неразбираемое значение заданий или его нет, **When** игра читает задания,
   **Then** выдаётся набор сегодняшнего дня с прогрессом 0 и `seen: false`, кошелёк гаража не
   меняется, разбор не бросает исключение.
3. **Given** у одного задания сохранён прогресс «-5» или «abc», остальные корректны, **When** игра
   читает задания, **Then** у этого задания прогресс 0, остальные задания сохраняют свой прогресс.
4. **Given** хранилище запрещено браузером, **When** игрок играет и забирает награды, **Then** всё
   работает до перезагрузки страницы, игра не падает.
5. **Given** сохранён набор за 2026-10-20, а часы устройства показывают 2026-10-19, **When** игра
   разбирает сохранение на 2026-10-19, **Then** остаётся действующим сохранённый набор 2026-10-20
   с его прогрессом и отметками (новый набор не создаётся).

### Edge Cases

- Заезд без монет, переключений и дистанции (авария сразу) — прогресс не меняется, все прибавки 0,
  ошибки нет.
- Один заезд выполняет сразу несколько заданий — все они в списке выполненных этим заездом.
- Прогресс никогда не превышает цель; «лишнее» не переносится ни на другие задания, ни на завтра;
  прибавка равна реально прибавленному.
- Монеты, полученные как награда за задание или автозачислением, НЕ считаются «собранными монетами».
- Итоги заезда с недопустимыми значениями — отказ `invalid-input`: не объект или не число —
  ошибка типа, отрицательное или дробное число — ошибка диапазона; задания и гараж не меняются.
- Смена дня во время открытой игры: учёт заезда сам актуализирует день; получение награды день не
  актуализирует, а отказывает с `stale-day`, если день в id задания раньше текущего; игра после
  этого вызывает актуализацию.
- Заезд через полночь: предпросмотр сам день не проверяет; по контракту UI вызывает его только при
  `state.day === dayKey(now)`, поэтому после полуночи всплывающих «выполнено» нет, а итоги в конце
  заезда идут в новый набор (FR-010).
- Переход часов назад не сбрасывает набор (ни при актуализации, ни при разборе сохранения), не даёт
  автозачисления и не позволяет повторно получить награды (FR-015, FR-018); награды выполненных
  заданий сохранённого набора можно забирать как обычно (FR-011).
- Сохранённая отметка «награда получена» у задания, которое по сохранённому прогрессу не выполнено, —
  трактуется как «награда получена» (повторно не выплачивается).
- Не удалось сохранить задания после изменения кошелька (хранилище отказало) — в текущей сессии
  награда считается полученной и повторно не выдаётся; игра узнаёт о сбое из результата сохранения.
- Начало следующего дня при переходе на летнее/зимнее время — это ближайшая следующая местная
  полночь, даже если сутки длятся 23 или 25 часов.

## Requirements *(mandatory)*

### Functional Requirements

**Задание и набор дня**

- **FR-001**: Задание MUST иметь: id вида `"<день>:<вид>"` (например `2026-10-19:coins`, уникален в
  пределах дня и между днями), вид (`coins` | `perfectShifts` | `distance`), уровень сложности
  (0 — лёгкое, 1 — среднее, 2 — сложное), цель (целое > 0), прогресс (целое, 0 ≤ прогресс ≤ цель),
  размер награды (целое > 0) и признак «награда получена». «Выполнено» — производное:
  прогресс = цель.
- **FR-002**: Состояние дня MUST содержать ключ дня (`YYYY-MM-DD`, местное время), ровно 3 задания —
  по одному каждого вида в порядке `coins`, `perfectShifts`, `distance` — и признак `seen`
  («игрок открывал экран заданий в этот день»). День к дню меняются уровни, цели и награды, состав
  видов одинаков.
- **FR-003**: Видов заданий в этой версии ровно три: «собрать монеты» (сумма монет за заезды),
  «идеальные переключения» (сумма идеальных переключений вверх), «проехать дистанцию» (сумма метров).
  Модель данных MUST допускать расширение пула видов позже: вид — это поле задания и запись в
  каталоге видов (что считается, из какой величины итогов заезда, уровни сложности), а правила
  прогресса, выполнения, награды и хранения не зависят от конкретного вида. Выбор 3 видов из
  более широкого пула — вне этой версии.
- **FR-004**: Выбор набора MUST быть детерминированным по дате: одна и та же дата всегда даёт один и
  тот же набор (уровни, цели, награды), независимо от числа перезапусков и от устройства. Набор дня
  MUST отличаться от набора предыдущего календарного дня хотя бы одной целью.
- **FR-005**: Цель каждого задания MUST определяться уровнем сложности вида по таблице контракта
  (раздел 2.5): монеты 60 / 150 / 300, идеальные переключения 3 / 8 / 12, дистанция
  1000 / 3000 / 6000 м; награда MUST быть фиксированной по уровню: 20 / 40 / 60 монет, одинаково
  для всех видов. Бонуса за выполнение всех трёх заданий дня нет.

**Прогресс**

- **FR-006**: Итоги заезда MUST учитываться в заданиях в тот момент, когда заезд заканчивается
  (авария или выход в меню через паузу), ровно один раз на заезд — в той же точке, где монеты заезда
  зачисляются в кошелёк гаража, и с тем гаражом, в который они уже зачислены.
- **FR-007**: Итоги заезда MUST состоять из: числа собранных монет, числа идеальных переключений и
  пройденной дистанции в целых метрах (дробная часть отбрасывается); все три — целые ≥ 0. Логика
  MUST уметь получать итоги из состояния заезда (мира); неверный мир — отказ `invalid-input`.
- **FR-008**: Учёт итогов MUST прибавлять значение соответствующего вида к прогрессу каждого
  невыполненного задания и ограничивать прогресс целью; выполненные задания MUST не меняться.
- **FR-009**: Учёт итогов MUST возвращать: прибавку по каждому заданию (`gains`: id → реально
  прибавленное, 0 если ничего), список заданий, ставших выполненными именно этим заездом
  (`completed`), а также результат актуализации дня (`autoCredited`, `dayChanged`) и гараж.
- **FR-010**: Учёт итогов MUST первым шагом выполнить актуализацию дня (FR-014…016) и затем
  учитывать итоги в актуальном наборе.
- **FR-010a**: Предпросмотр (`previewCompleted`) MUST по состоянию и итогам текущего заезда
  возвращать id заданий, которые эти итоги впервые довели бы до цели (уже выполненные не входят),
  и MUST не менять ни состояние, ни что-либо ещё; день он не проверяет. Неверные итоги — отказ
  `invalid-input`.

**Награда**

- **FR-011**: Забрать награду MUST быть возможно только за задание, день в id которого не раньше
  текущего дня, которое есть в сохранённом наборе, выполнено и за которое награда ещё не получена.
  Если текущий день раньше дня состояния (часы переведены назад), награда за задание сохранённого
  набора MUST выдаваться как обычно.
- **FR-012**: Успешное получение награды MUST увеличить кошелёк гаража ровно на размер награды,
  отметить задание «награда получена» и вернуть `{ state, garage, reward }`; уровни улучшений гаража
  MUST не меняться. Получение награды MUST не выполнять актуализацию дня и автозачисление.
- **FR-013**: Отказ в получении награды MUST быть ошибкой с полем `code` и текстом на русском и MUST
  оставлять задания и кошелёк без изменений. Проверки идут в порядке:
  1. неверный ввод (id не строка, неверный ключ дня, неверное состояние/гараж) — `invalid-input`;
  2. день в id раньше текущего дня — `stale-day`, «Задания устарели — наступил новый день»;
  3. задания нет в сохранённом наборе — `unknown-mission`, «неизвестное задание: "<id>"» (текст для
     логов; игроку UI показывает общий текст, контракт, раздел 4);
  4. задание не выполнено — `not-completed`, «Задание ещё не выполнено: <прогресс> из <цель>»;
  5. награда уже получена — `already-claimed`, «Награда за задание уже получена».

**Смена дня**

- **FR-014**: Если текущий день позже дня состояния, актуализация MUST заменить набор набором
  текущего дня с нулевым прогрессом и `seen: false` и вернуть `dayChanged: true`.
- **FR-015**: Если текущий день равен дню состояния или раньше его (часы переведены назад),
  актуализация MUST вернуть состояние и гараж без изменений, `autoCredited: 0`, `dayChanged: false`.
- **FR-016**: При смене дня (FR-014) награды за выполненные, но не забранные задания прежнего
  набора MUST автоматически зачисляться в кошелёк гаража; актуализация MUST возвращать
  `{ state, garage, autoCredited, dayChanged }`, где `autoCredited` — сумма автозачисления (0, если
  зачислять нечего). Невыполненные задания ничего не дают. Автозачисление происходит ровно один раз:
  набор, по которому оно сделано, заменяется новым. Пропущенные дни между днём состояния и текущим
  ничего не начисляют.
- **FR-016a**: Смену дня (с автозачислением) MUST выполнять только актуализация дня
  (`ensureMissionDay`); учёт заезда вызывает её первым шагом. Получение награды день не
  актуализирует: оно сравнивает день в id задания с текущим днём и, если день в id раньше,
  отказывает `stale-day`, ничего не меняя; автозачисление вчерашней награды происходит при
  следующей актуализации, которую вызывает игра. Если день в id позже текущего (часы переведены
  назад), задание ищется в сохранённом наборе как обычно.
- **FR-016b**: Логика MUST по моменту времени возвращать момент начала следующих местных суток
  (`nextDayStart`) — ближайшую местную полночь строго после заданного момента; неверный момент —
  `invalid-input`.

**Просмотр**

- **FR-016c**: Операция «отметить просмотренным» (`markMissionsSeen`) MUST возвращать новое
  состояние с `seen: true`, не меняя задания; повторный вызов даёт тот же результат. Признак `seen`
  MUST сбрасываться в `false` при смене дня (FR-014) и сохраняться между перезапусками.

**Хранение и повреждённые данные**

- **FR-017**: Состояние дня (ключ дня, задания с прогрессом и отметками о наградах, `seen`) MUST
  сохраняться отдельно от гаража, под своим ключом хранилища, после каждого изменения (учёт заезда,
  получение награды, смена дня, отметка просмотра) и переживать перезагрузку страницы.
- **FR-018**: Разбор сохранения (`parseMissions`) MUST быть терпимым и при корректном ключе дня
  никогда не бросать: отсутствующее или неразбираемое значение, неверный день, не тот состав или
  порядок видов, id не того вида — новый набор на сегодня с нулевым прогрессом и `seen: false`;
  некорректный прогресс отдельного задания — 0, прогресс больше цели — цель; некорректный `seen` —
  `false`; уровни, цели и награды берутся из правил набора дня сохранённого дня, а не из сохранения.
  Корректный набор с днём позже `day` (часы переведены назад) MUST оставаться действующим.
- **FR-019**: Повреждение или недоступность сохранения заданий MUST не влиять на кошелёк и улучшения
  гаража и MUST не ронять игру; при недоступном хранилище задания работают до перезагрузки, а игра
  узнаёт об успехе или сбое сохранения.
- **FR-020**: После любого изменения кошелька (получение награды, автозачисление) MUST сохраняться и
  гараж, и задания; монеты из награды MUST не зачисляться повторно после перезагрузки.

**Проверка входа и ошибки**

- **FR-021**: Каждая операция логики, принимающая внешний ввод (момент времени, ключ дня, состояние,
  гараж, итоги заезда, мир, id задания), MUST первым шагом проверять его и при плохом вводе
  отказывать ошибкой с `code: "invalid-input"` и понятным текстом, не меняя состояние: неверный тип
  (не число, не строка, не объект) — ошибка типа (`TypeError`), неверное значение (отрицательное или
  дробное число, дата `2026-13-45`) — ошибка диапазона (`RangeError`), как в гараже.
- **FR-021a**: Все ошибки логики заданий MUST иметь поле `code` из набора: `invalid-input`,
  `stale-day`, `unknown-mission`, `not-completed`, `already-claimed` (контракт, раздел 4). Нарушения
  правил (все коды, кроме `invalid-input`) — ошибки диапазона (`RangeError`).
- **FR-022**: Логика заданий MUST не зависеть от экрана, хранилища и системных часов: текущий момент
  и ключ дня передаются ей извне; исходные состояния не изменяются, возвращаются новые; экранных
  текстов заданий логика не формирует (их строит UI по виду задания), кроме сообщений об ошибках.

**Совместимость**

- **FR-023**: Существующее поведение гаража (зачисление монет заезда, покупки, цены, разбор
  сохранения) MUST сохраниться без изменений; задания только добавляют монеты в тот же кошелёк.

### Key Entities *(include if feature involves data)*

- **Вид задания** (`type`, запись каталога видов): `coins` | `perfectShifts` | `distance`; что
  считается, из какой величины итогов заезда, цели трёх уровней сложности (FR-005). Новый вид
  добавляется записью в каталог (FR-003).
- **Задание**: `id` (`"<день>:<вид>"`), `type`, `level` (0/1/2), `target`, `reward`, `progress`,
  `claimed`; «выполнено» — производное (`progress === target`).
- **Состояние дня**: `{ day, missions: [coins, perfectShifts, distance], seen }`. Сохраняется
  отдельно от гаража; `seen` сбрасывается в новый день.
- **Итоги заезда**: `{ coins, perfectShifts, distance }` — целые ≥ 0, `distance` — целые метры,
  получаются из мира.
- **Результат учёта заезда**: новое состояние, гараж, `autoCredited`, `dayChanged`, `gains`,
  `completed`.
- **Результат актуализации дня**: новое состояние, гараж, `autoCredited` (целое ≥ 0), `dayChanged`.
- **Ошибка логики заданий**: тип ошибки, `code` (FR-021a), текст на русском.
- **Гараж (существующий)**: кошелёк монет и уровни улучшений; задания только увеличивают кошелёк
  (получение награды и автозачисление при смене дня).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В 100% проверок одна и та же дата даёт один и тот же набор из 3 заданий в порядке
  монеты / переключения / дистанция; на 365 подряд идущих датах ни один набор не совпадает с набором
  предыдущего дня.
- **SC-002**: Итоги каждого завершённого заезда попадают в прогресс ровно один раз — 0 случаев
  двойного учёта или потери в сквозной проверке «авария» и «выход в меню через паузу».
- **SC-003**: Каждая награда зачисляется в кошелёк ровно один раз, если задание выполнено (вручную
  или автоматически при смене дня), и ни разу — если не выполнено, в том числе после перезагрузки
  страницы; все пять отказов из FR-013 оставляют кошелёк и задания неизменными.
- **SC-004**: Любое повреждённое или недоступное сохранение заданий не приводит к падению игры и не
  меняет кошелёк — 100% сценариев User Story 6.
- **SC-005**: По замеру симуляцией (автопилот, 30 трасс) лёгкое задание выполняется примерно за
  1 заезд, среднее — за 2–3, сложное — примерно за 5.
- **SC-006**: Предпросмотр в 100% проверок не меняет состояние и совпадает со списком `completed`,
  который дал бы учёт тех же итогов в тот же день.
- **SC-007**: Все существующие проверки гаража и игры продолжают проходить без изменений.

## Assumptions

- **День** — календарная дата по местному времени устройства игрока; смена — в 00:00 местного
  времени. Серверного времени нет (игра офлайн).
- **Выбор набора** — детерминированный по дате (источник случайности инициализируется от даты),
  поэтому перезапуски не «перебрасывают» задания; уровень сложности каждого задания выбирается
  случайно в этом смысле.
- **Уровни сложности и награды** — принцип (3 уровня, фиксированная награда 20/40/60) решён
  владельцем продукта; цели взяты из контракта (раздел 2.5) по замеру симуляцией (автопилот,
  30 трасс: заезд до аварии ≈ 57–104 монеты, 2 идеальных переключения, 840–1500 м) и остаются
  допущением до плейтеста:

  | Вид | Лёгкое (награда 20) | Среднее (награда 40) | Сложное (награда 60) |
  |---|---|---|---|
  | Собрать монеты | 60 | 150 | 300 |
  | Идеальные переключения | 3 | 8 | 12 |
  | Проехать дистанцию, м | 1000 | 3000 | 6000 |

- Прогресс в состоянии меняется только по завершённым заездам; во время заезда — только
  предпросмотр без изменения состояния.
- «Идеальное переключение» — то же, что уже считается в игре (переключение вверх в окне оборотов
  [0.82, 1)); дистанция — пройденный путь машины за заезд.
- Монеты из наград не идут в прогресс «собрать монеты»; задания не дают других наград, кроме монет.
- Состояние заданий хранится под ключом хранилища `metro-rush-missions`, отдельно от гаража, по
  правилу конституции «один ключ на область» (контракт, раздел 5).
- Один игрок на устройство, без аккаунтов и синхронизации между устройствами.
- Экраны, кнопки, тексты заданий по виду, всплывающие надписи и сообщения об автозачислении —
  вне этой спеки (UI-спека и контракт, разделы 4–6).
