# ДЗ 5: GitHub Spec Kit и сравнение с OpenSpec

Фича: **ежедневные задания** в Metro Rush. Две «команды» (два изолированных чата-агента) писали
спеку UI и спеку логики, согласовали общий контракт и только потом реализовали всё одним целым.

## 1. Что такое Spec Kit

Набор от GitHub для spec-driven development: CLI `specify` (Python, ставится через `uv`) создаёт в
проекте папку `.specify/` (шаблоны, скрипты, «конституция») и команды для агента. Версия в проекте —
**1.0.13**, интеграции Claude Code (`/speckit-*`) и OpenCode (`/speckit.*`).

Шаги Spec Kit:

| Команда | Что делает | Что получилось у нас |
|---|---|---|
| `constitution` | принципы проекта, которые проверяются в каждом плане | 6 принципов: 5 из style guide + «UI и логика согласуются через контракт до кода» |
| `specify` | спека «что и зачем»: истории P1–P3, Given/When/Then, FR-001…, критерии успеха, без технологий | `001-daily-missions-ui`, `002-daily-missions-logic` — каждая своей командой |
| `clarify` | вопросы человеку по меткам `[NEEDS CLARIFICATION]` (до 3) | 4 решения владельца: вчерашняя награда, где забирать, виды заданий, награды |
| `plan` | техплан + проверка конституции + research, data-model, contracts/, quickstart | `003-daily-missions/plan.md`, все 6 принципов ✅ |
| `tasks` | задачи по историям с ID и путями | 31 задача, 9 фаз |
| `analyze` | проверка согласованности spec ↔ plan ↔ tasks ↔ конституция (только чтение) | 4 находки, 3 исправлены до кода |
| `implement` | реализация по задачам с отметками `[X]` | 31/31, `CHECK: PASS` |

## 3. Spec Kit и OpenSpec на нашем опыте

| | OpenSpec (практика 5, гараж) | Spec Kit (ДЗ 5, задания) |
|---|---|---|
| Главная идея | живые спеки системы + change с **дельтой** (ADDED/MODIFIED) | **папка на фичу** с полной спекой; общей спеки системы нет |
| После завершения | `sync` вливает дельту в `openspec/specs/`, `archive` убирает change в историю | ничего не сливается, папки `001-…`, `002-…` копятся |
| Общие правила проекта | `config.yaml`: `context` и `rules` по артефактам (мы добавили правило Mermaid для design) | `constitution.md` с версией; план обязан пройти «ворота конституции» |
| Документы | proposal, delta specs, design, tasks | spec, plan, research, data-model, contracts/, quickstart, tasks, checklists |
| Уточнения у человека | вручную через review → `update` | встроенный шаг `clarify` с метками в спеке |
| Контракты между частями | отдельного места нет (можно в design) | папка `contracts/` прямо в плане — удобно для «двух команд» |
| Проверка | `openspec validate --strict` — CLI, без модели, детерминированно | `analyze` — проверяет модель, результат может отличаться |
| Подходит лучше | доработка существующего кода (brownfield): видно, **что меняется** | новая фича с нуля: видно, **что строим целиком** |
| Что неудобно | нет места для согласования двух спек | спека на фичу, а не на две — пришлось завести объединяющую `003` для plan/implement |

## 4. Выводы

- **Обе спеки до кода — это работает.** Расхождения нашлись на бумаге (15 за две итерации), а не в
  коде: ни одно из них не пришлось исправлять после реализации.
- **Изоляция команд важна.** В одном чате агент сам бы всё «подогнал» и расхождений бы не было.
- **Согласование надо вовремя остановить.** Каждая итерация находила всё более редкие случаи;
  мы записали их как принятые ограничения.
- **Проверки ловят ошибки плана.** Тест на 365 днях опроверг правило из research, и его заменили до
  сдачи; `analyze` нашёл нестабильный браузерный тест до того, как он был написан.
- **Решения принимает человек:** 4 ответа в clarify, 9 + 6 решений по контракту, остановка
  согласования.
