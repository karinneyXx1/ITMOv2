# E2E-проверки

Сквозные сценарии повторяют use case из [`product_management.md`](product_management.md): разработчик отправляет diff на `POST /api/reviews` и получает ответ, по которому сам принимает решение о PR (SCOPE-1). Сервис поднят целиком (FastAPI `app`, `ReviewService`, зависимость из `app.dependencies`); внешний LLM заменён контролируемой реализацией протокола `LLM` (`review_service.py:4-6`), так как реальная реализация неизвестна (`context.md`). В качестве входа используется сам `TRAINING_PR.diff` (1 060 байт — укладывается в лимит API-1) и его модификации.

| Сценарий пользователя | Предусловия | Действие | Наблюдаемый результат | Evidence |
|---|---|---|---|---|
| Позитивный | Сервис запущен, `GET /health` → `{"status": "ok"}` (`api.py:13-15`); контролируемый LLM возвращает структурированный ответ с 3 рисками из P1-02 (SEC-1 `review_service.py:14`, API-1 `api.py:10`, REL-1 `review_service.py:15`) и списком проверок | Разработчик отправляет `POST /api/reviews` с `{"diff": "<содержимое TRAINING_PR.diff>"}` | HTTP 200 за ≤ 10 с; тело содержит `summary`, `risks` из 3 элементов с полями `file`, `line`, `evidence`, `risk` и `checks` (OUT-1); каждый `evidence` — строка, присутствующая в отправленном diff (QA-1); `file` ∈ {`app/review_service.py`, `app/api.py`}; в ответе нет полей/действий approve, merge, изменения кода (SCOPE-1); в логе одна запись с `request_id`, длительностью, статусом 200 и без текста diff (OBS-1) | Формат OUT-1; P1-02 «Risks (3)» как эталон структурированного ответа; сейчас `review_service.py:16` вернул бы `{"comment": "..."}` |

## Как использовали AI

- Для чего: составление сквозных сценариев пользователя «разработчик → `POST /api/reviews` → ответ по OUT-1» на самом `TRAINING_PR.diff` и его модификациях, с наблюдаемыми результатами по правилам SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1 и привязкой к рискам P1-02.
- Тип промпта: master prompt (build).
- Строка в [`prompts.md`](prompts.md): P1-03.
- Что проверили и исправили сами: сверила сценарий "Граничный (целостность патча)" с таблицей несовпадений из P1-02 (заголовки @@ -1,10 +1,23 и -1,8 +1,17 против реальных 10/16 и 10/15) — совпадает. Проверила, что позитивный сценарий описывает реальный формат OUT-1, а не старый {"comment": answer}.
