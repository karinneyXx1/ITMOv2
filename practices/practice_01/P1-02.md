# P1-02 — AI Review: TRAINING_PR.diff

Роль: senior reviewer (только анализ; без approve/merge/правок).
Источники: `TRAINING_PR.diff` + Context Pack (SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1). Внешние источники и другие файлы не использовались.

## Summary

PR добавляет метод `ReviewService.review()` и эндпоинт `POST /api/reviews`, который берёт `payload["diff"]` и целиком подставляет его в промпт внешнего LLM. В коде подтверждены три нарушения правил Context Pack: отсутствие удаления секретов перед отправкой в LLM (SEC-1), отсутствие лимита размера diff / ответа 413 (API-1), отсутствие таймаута и контролируемой обработки ошибок LLM-вызова (REL-1). Отдельно: сам diff как патч некорректен — счётчики строк в заголовках `@@` не совпадают с фактическим телом хунков в обоих файлах, поэтому `git apply` с высокой вероятностью отклонит патч.

Номера строк ниже указаны по итоговому файлу и восстановлены по телу хунков (оба хунка начинаются с `+1`), а не по счётчикам в заголовках, поскольку заголовки недостоверны (см. раздел «Целостность diff»).

## Risks (3)

### Risk 1 — секреты из diff уходят во внешний LLM без очистки
- **file:** `app/review_service.py`
- **line:** 14 (формирование промпта), отправка — строка 15
- **evidence:**
  ```python
  prompt = f"Review this pull request and find problems:\n{diff}"
  answer = self.llm.generate(prompt)
  ```
- **rule:** SEC-1 — «перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи». Между получением `diff` и вызовом `self.llm.generate(prompt)` нет никакого шага редактирования/маскирования; `diff` подставляется в промпт как есть.

### Risk 2 — нет ограничения размера diff и ответа HTTP 413
- **file:** `app/api.py`
- **line:** 10
- **evidence:**
  ```python
  return review_service.review(payload["diff"])
  ```
- **rule:** API-1 — «diff длиннее 20 000 символов отклоняется с HTTP 413». В эндпоинте нет проверки `len(payload["diff"])` и нет возврата 413; значение передаётся в сервис напрямую, а в `review_service.py:13-16` проверки длины тоже нет.

### Risk 3 — LLM-вызов без таймаута и без контролируемого ответа на ошибку
- **file:** `app/review_service.py`
- **line:** 15
- **evidence:**
  ```python
  answer = self.llm.generate(prompt)
  ```
  и сигнатура протокола (строка 5): `def generate(self, prompt: str) -> str:`
- **rule:** REL-1 — «внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ». В diff вызов не обёрнут в `try/except`, таймаут не передаётся, интерфейс `LLM.generate` не имеет параметра таймаута; исключение провайдера поднимется до FastAPI как необработанное (500).
- **оговорка:** таймаут теоретически может быть реализован внутри конкретной реализации LLM в `app.dependencies` — это открытый вопрос (см. ниже). Но вторая часть правила (превращение ошибки в контролируемый ответ) в diff отсутствует независимо от реализации.

## Целостность diff как патча (отдельная проверка)

Подсчёт по телу хунков (контекст ` ` / удалено `-` / добавлено `+`):

| Хунк | Заголовок | Факт: старых строк | Факт: новых строк | Статус |
|---|---|---|---|---|
| `app/review_service.py` `@@ -1,10 +1,23 @@` | old=10, new=23 | 9 контекст + 1 `-` = **10** | 9 контекст + 7 `+` = **16** | old OK, new FAIL (23 != 16) |
| `app/api.py` `@@ -1,8 +1,17 @@` | old=8, new=17 | 10 контекст + 0 `-` = **10** | 10 контекст + 5 `+` = **15** | old FAIL (8 != 10), new FAIL (17 != 15) |

**Вывод:** diff не является корректным патчем — в трёх из четырёх счётчиков расхождение. `git apply` / `patch` такой файл, скорее всего, отклонят («corrupt patch»). Это не риск кода, а риск артефакта ревью: неясно, был ли diff отредактирован вручную и соответствует ли он реальному состоянию ветки. Требуется перегенерация diff из git.

## Checks

1. **SEC-1:** отправить на `POST /api/reviews` diff, содержащий тестовый `token=...` / `-----BEGIN PRIVATE KEY-----`; перехватить `prompt`, переданный в `LLM.generate` (mock-реализация `LLM`), и убедиться, что секрет заменён на `[REDACTED]`. Сейчас ожидаемо провалится.
2. **API-1:** отправить diff длиной 20 001 символ; ожидать HTTP 413. Сейчас ожидаемо провалится (запрос уйдёт в LLM).
3. **REL-1 (таймаут):** mock `LLM.generate`, который спит > 10 с; ожидать контролируемый ответ до ~10 с. **REL-1 (ошибка):** mock, выбрасывающий исключение; ожидать контролируемый ответ (не 500 с трассировкой).
4. **Целостность патча:** выполнить `git apply --check TRAINING_PR.diff` на базовом коммите (`21bf12a`, `7c99aa1`) — ожидается ошибка из-за неверных счётчиков; перегенерировать diff через `git diff`.
5. **Вход без `diff` (без правила в Context Pack):** `POST /api/reviews` с `{}` → в `api.py:10` `payload["diff"]` даст `KeyError` → 500. В Context Pack нет правила про валидацию схемы входа, поэтому это не оформлено как risk, а вынесено как проверка/вопрос владельцу правил.

## Открытые вопросы (данных недостаточно, не додумываю)

- **Версия Python:** в diff используется `dict[str, str]` в аннотациях (`review_service.py:13`, `api.py:9,14`), что требует Python 3.9+. Версия в предоставленных источниках не зафиксирована — совместимость проверить нельзя.
- **Реализация LLM в `app.dependencies.review_service`:** неизвестно, есть ли внутри таймаут/ретраи; влияет на строгость Risk 3, но не отменяет отсутствия обработки ошибок в diff.
- **Аутентификация на `/api/reviews`:** по diff эндпоинт открыт; правила про auth в Context Pack нет — риск не формулирую.
- **OBS-1:** в diff нет логирования вообще; нарушения правила «в лог пишутся только request_id, длительность и статус» по diff подтвердить нельзя (нет evidence) — риск не включён.
