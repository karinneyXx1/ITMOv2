# Отчёт 1. Атаки на исходный сервис

Стенд — `practices/practice_06/lab`, намеренно уязвимый Mini Shop. Данные синтетические,
сервис слушает только `127.0.0.1`. Находки подтверждены регрессионными тестами
`lab/test_security.py`: каждый тест утверждает безопасное поведение, и на исходном
`service.py` **все 15 проверок падают** — это и есть доказательство дыр до исправления.

```
Ran 14 tests in 0.025s
FAILED (failures=15)   # 14 тест-методов, один из них с двумя subTest
```

Поставляемые функциональные тесты (`test_service.py`, `test_http.py`) при этом проходят —
значит, сервис рабочий, проблема именно в безопасности.

## Детали

### T1. Роль берётся из клиентского заголовка
`/admin/export` сверяет `headers.get("X-Role") != "staff"`. Заголовок полностью под
контролем клиента, поэтому обычный клиент добавляет `X-Role: staff` и выгружает все
профили. Роль обязана определяться по сессии (`X-Token`), а не по запросу.

### T2. Цена заказа принимается из тела
В `POST /orders` цена берётся как `body.get("price", self.products[product])`. Клиент
присылает `price: 1` и покупает стул за 1 рубль. Цену должен назначать сервер по каталогу.

### T3. Отладочный журнал открыт всем
`GET /debug/logs` отдаёт весь список `self.logs`, куда на каждый запрос пишутся тело и
заголовки — включая токены сессий и пароли из `POST /login`. Доступен без авторизации.

### T4. Чтение чужого профиля (152-ФЗ)
`GET /profile?id=...` не требует сессии и не привязан к владельцу: `id` берётся из запроса.
Клиент читает профиль любого пользователя — прямое раскрытие персональных данных.

### T5. SQL-инъекция в профилях и поиске
`/profile` и `/search` собирают запрос форматированием строки:
`SELECT * FROM profiles WHERE id = {query['id']}` и `... LIKE '%{q}%'`. Значения из URL
попадают в SQL без параметризации, что позволяет изменить условие и выгрузить всю таблицу.

### T6. IDOR при выдаче файлов
`GET /files` строит путь из `user`/`path` запроса и отдаёт содержимое без привязки к
сессии. Физическую границу каталога `sandbox.py` удерживает, но **внутри** границы клиент
читает и чужой чек, и служебную заметку оператора. Это разграничение — зона `service.py`.

### T7. Клиент напрямую управляет инструментами помощника
`POST /assistant/execute` исполняет любое присланное `decision` без авторизации и без
привязки к владельцу: `export_profiles` выгружает все ПДн, `read_file` читает чужой файл,
`delete_tree` удаляет учебные данные (в пределах песочницы, восстанавливается перезапуском).

### T8. Нет серверной защиты, независимой от модели
Это ключевая проблема AI-интеграции. Отзывы из `/reviews` без фильтрации попадают в
контекст помощника (`/assistant/context`), то есть недоверенный текст может подменить
инструкцию модели (prompt injection). Но даже независимо от послушания модели сервер
обязан отклонять опасные решения — сейчас он слепо исполняет `delete_tree`/`export_profiles`,
присланные как валидный JSON. «Мозг» (LLM) и «руки» (исполнение) не разделены.

### T9. Stored XSS в просмотре отзывов
`GET /reviews/view` вставляет текст отзыва в HTML без экранирования:
`"".join(f"<p>{r['text']}</p>" ...)`. Отзыв `<script>alert(1)</script>` сохраняется и
исполняется в браузере у каждого, кто откроет страницу.

## Вывод

Сервис рабочий, но нарушает все три границы доверия из модели угроз: доверяет данным из
запроса (роль, цена, id, путь), не параметризует SQL, не экранирует вывод и исполняет
решения AI-помощника без серверной проверки. Исправления и повторная проверка — в
[REPORT_02.md](REPORT_02.md); план мер — в [THREAT_MODEL.md](THREAT_MODEL.md).
