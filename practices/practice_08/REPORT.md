# Практика 8: фронтенд для «Код-репетитора»

Фронтенд я делала для своего основного проекта на курсе, сервиса [tutor-hub](https://github.com/karinneyXx1/tutor-hub). Это сервис для репетитора по программированию и его учеников. Сервер на FastAPI и SQLite у меня уже был, теперь к нему добавился интерфейс в папке `frontend/`.

- Код фронтенда и тесты: [tutor-hub/frontend](https://github.com/karinneyXx1/tutor-hub/tree/main/frontend), pull request [#16](https://github.com/karinneyXx1/tutor-hub/pull/16)
- Макет: https://tutor-hub-mockup.vercel.app (опубликованный прототип из v0) и [чат v0](https://v0.app/karinagn2007-9022/chat/-mb8Gus4oI8c) с моими запросами
- Тесты в CI: [запуск GitHub Actions](https://github.com/karinneyXx1/tutor-hub/actions/runs/43877346951), вывод локального запуска в [test-run.txt](test-run.txt)
- Как должен вести себя интерфейс: [docs/frontend-spec.md](https://github.com/karinneyXx1/tutor-hub/blob/main/docs/frontend-spec.md)

Стек: React 19, TypeScript, Vite, Tailwind CSS и библиотека компонентов shadcn/ui. Тесты на Vitest, React Testing Library, MSW и Playwright.

## Что делает интерфейс

Основной сценарий: репетитор выдаёт ученику домашнее задание.

Репетитор входит по email и паролю и попадает на страницу «Домашние задания». Там сводка по статусам и список уже выданных заданий. Он нажимает «Выдать задание», в окне выбирает ученика, пишет название, при желании описание и ставит срок. После нажатия «Выдать задание» окно закрывается, новое задание появляется в списке, а сверху выводится сообщение, что задание выдано. Задание сохраняется на сервере, и ученик видит его у себя, если войдёт под своим аккаунтом.

Всё работает с настоящим API: вход, список учеников, список заданий и создание задания. Форма проверяет те же правила, что и сервер: название не может быть пустым или состоять из одних пробелов, срок не может быть в прошлом. Ошибки сервера я перевела в понятные сообщения на русском.

Как запустить:

```bash
make install        # один раз
make run            # сервер, http://localhost:8000
make run-frontend   # интерфейс, http://localhost:5173 (во втором терминале)
make demo-data      # демо-пользователи и задания, вход tutor@example.com / demo-password
```

## Макет

Макет я делала в v0. Оба запроса сохранены в [mockup/v0-prompt.md](mockup/v0-prompt.md).

В первом запросе я описала, кто пользуется сервисом и что он должен сделать, три экрана (вход, список, окно с формой) и все состояния: загрузку, пустой список, ошибки, сохранение и успех. Попросила использовать только компоненты shadcn/ui, индиго как основной цвет, подписи у полей, видимый фокус и нормальный вид на телефоне. Чтобы состояния было удобно смотреть, попросила добавить сверху переключатель.

v0 сразу сделал тёмную тему, логотип `</>`, карточки с цветным статусом и подпись «Описание (необязательно)». Все экраны и состояния были на месте ([вход](mockup/v0-v1-login.png), [список](mockup/v0-v1-list.png), [форма](mockup/v0-v1-dialog.png)). Но выглядело это слишком просто: одинаковые карточки, никакой сводки, в карточке не видно описания задания, у срока сдачи нет подсказки. Ещё я не написала в первом запросе, что выбор ученика должен быть обычным выпадающим списком, а ошибки нужно показывать под полем. Это важно для работы с клавиатуры и для тестов.

Во втором запросе я попросила:
- сводку по статусам над списком;
- цветную полоску у карточки, аватар ученика с инициалами, описание задания и пометку «просрочено»;
- более живое пустое состояние, загрузку в форме карточек и ошибку загрузки с кнопкой «Повторить»;
- лёгкое свечение фона;
- обычный выпадающий список для выбора ученика, ошибки под полями и подсказку к сроку;
- раскладку для телефона.

Итоговый вариант: [вход](mockup/v0-v2-login.png), [пустой список](mockup/v0-v2-empty.png), [список](mockup/v0-v2-list.png), [форма](mockup/v0-v2-dialog.png). Всё, что есть в макете, считается из данных, которые сервер уже отдаёт, так что новые эндпоинты не понадобились.

## Библиотека компонентов и тема

Я выбрала shadcn/ui, как в лекции. Её компоненты добавляются прямо в проект (`frontend/src/components/ui/`), поэтому их легко подстроить под свой дизайн. Все кнопки, поля, карточки, окно с формой, статусы, аватары, сообщения об ошибках и заглушки загрузки взяты из неё. Своих кнопок и полей я не писала. Чтобы AI-агент тоже не писал свои, я добавила это правило в [AGENTS.md](https://github.com/karinneyXx1/tutor-hub/blob/main/AGENTS.md).

Цвета, шрифт и скругления заданы в одном файле, [`frontend/src/index.css`](https://github.com/karinneyXx1/tutor-hub/blob/main/frontend/src/index.css). Там основной индиго, цвет фокуса, цвета ошибок и успеха и отдельные цвета для каждого статуса задания. Шрифт Geist, отступы по стандартной шкале Tailwind. В компонентах цвета пишутся только через эти переменные, конкретных значений вроде `#4f46e5` в коде нет.

## Доступность

У каждого поля есть подпись. Если поле заполнено неправильно, под ним появляется сообщение, а фокус переходит на первое такое поле. Весь сценарий можно пройти с клавиатуры: Tab, Enter, а Escape закрывает окно. У кнопок и полей в фокусе видно индиго-кольцо. На ширине 375 px ничего не уезжает за экран.

## Повторная отправка

Пока задание сохраняется, кнопка блокируется и пишет «Сохраняем…». Одной блокировки недостаточно: если нажать дважды очень быстро, второе нажатие успевает проскочить до того, как кнопка заблокировалась. Поэтому в [`useSingleFlight`](https://github.com/karinneyXx1/tutor-hub/blob/main/frontend/src/hooks/useSingleFlight.ts) есть ещё флаг «запрос уже идёт», который проверяется в самом начале отправки. Пока запрос не закончился, второй не отправится, даже если нажать Enter. Окно формы во время сохранения тоже нельзя закрыть.

Если сервер ответил ошибкой, введённые данные остаются в форме, и можно сразу отправить ещё раз.

## Тесты

```bash
make test-frontend   # Vitest: 41 тест
make test-e2e        # Playwright: 5 тестов
```

Все тесты проходят и локально, и в GitHub Actions.

Тесты компонентов написаны на Vitest и React Testing Library. Они ищут элементы так же, как пользователь: по подписям, кнопкам и тексту. Ответы сервера подменяет MSW. Ответы по умолчанию заданы в [`src/test/server.ts`](https://github.com/karinneyXx1/tutor-hub/blob/main/frontend/src/test/server.ts), в отдельных тестах я их меняю: успешный ответ, пустой список, задержка, ошибки 401, 422 и 500 и отсутствие сети. Тестовые данные в [`fixtures.ts`](https://github.com/karinneyXx1/tutor-hub/blob/main/frontend/src/test/fixtures.ts) повторяют формат ответов из `backend/app/schemas.py`. Если тест отправит запрос, на который не задан ответ, он упадёт, так что пройти «случайно» он не может.

Что проверяют тесты:
- поля, кнопки, карточки, сводку по статусам, ввод текста и выбор ученика;
- открытие окна формы с двух кнопок и закрытие через «Отмена», Escape и крестик. При повторном открытии форма пустая;
- обязательные поля, название из пробелов, срок в прошлом, неправильный email, слишком длинный текст и отказ сервера по сроку. Сообщения появляются под полями и пропадают, когда поле исправляешь;
- загрузку, пустой список, список, ошибку сервера с кнопкой «Повторить», отсутствие сети и ошибку при сохранении;
- повторную отправку: двойной клик и Enter во время сохранения, отдельно два нажатия быстрее, чем обновится экран. В обоих случаях уходит один запрос;
- весь сценарий целиком: вход, пустой список, заполнение формы, задание в списке.

Браузерные тесты на Playwright проходят сценарий в настоящем Chrome: обычный, только с клавиатуры, с двойным кликом и на узком экране. Ещё один тест работает с настоящим сервером. Он регистрирует пользователей, выдаёт задание через интерфейс, перезагружает страницу и проверяет, что задание сохранилось.

Чтобы убедиться, что тесты действительно что-то ловят, я по очереди ломала код и смотрела, падают ли они:

| Что сломала | Что упало |
|---|---|
| убрала флаг «запрос уже идёт» | тест на два быстрых нажатия (сначала его не было, см. ниже) |
| убрала блокировку кнопки | тест на двойной клик и Enter |
| убрала вывод ошибки сервера в форме | тест на ошибку 500 при сохранении |
| разрешила название из пробелов | 2 теста проверки полей |
| убрала кольцо фокуса у кнопки | браузерный тест с клавиатуры |
| убрала подменённый ответ со списком учеников | 16 тестов |

Когда возвращала код обратно, всё снова проходило.

## Как я использовала AI

Макет делала в v0, а код, тесты, CI и документацию писала вместе с Claude. Скриншоты снимал Playwright.

Примеры того, что я просила у агента (своими словами, в чате):
- сделать фронтенд к tutor-hub на React, TypeScript и shadcn/ui для сценария «репетитор выдаёт задание», брать только компоненты shadcn/ui, тему вынести в одно место, учесть загрузку, пустой список, ошибки и двойную отправку;
- описать поведение формы так же, как в spec.md из лекции. Из этого получился [docs/frontend-spec.md](https://github.com/karinneyXx1/tutor-hub/blob/main/docs/frontend-spec.md);
- предложить тесты на компоненты и окно формы, проверку полей, состояния с подменой ответов сервера, двойную отправку и весь сценарий. Проверять то, что видит пользователь, а не внутренности кода;
- по очереди сломать защиту от двойной отправки, вывод ошибки и проверку пробелов и убедиться, что тесты падают;

Что пришлось исправить после AI:
- **Тест на двойную отправку проходил даже без защиты.** В тесте между кликами кнопка успевала заблокироваться. Я заметила это, когда ломала код, и добавила тест на два нажатия быстрее обновления экрана.
- **Тест фокуса проходил всегда.** Он проверял только, что у кнопки «есть хоть какая-то тень», а она есть всегда. Теперь он проверяет именно кольцо фокуса и падает, если кольцо убрать.
- **Строгий режим подмены ответов не работал.** В новой версии MSW опцию переименовали, и запросы без подменённого ответа проходили молча. Это нашлось при проверке типов, я поменяла название опции.
- **Заголовок «Вход» не был заголовком,** и экранный диктор его не находил. Это поймал тест.
- **Пункт списка «Выберите ученика» совпадал с текстом ошибки,** и было непонятно, что из этого ошибка. Переименовала пункт в «— не выбран —».
- **Заглушки загрузки были почти не видны.** Заметила на скриншоте и сделала их заметнее.
- **Форма сбрасывалась лишним способом,** на это ругался линтер. Переделала так, чтобы окно формы каждый раз открывалось заново.
- **Браузерный тест с клавиатуры не мог выбрать ученика стрелкой** в Chrome без окна. Там выбор сделан напрямую, а весь остальной путь по-прежнему проходит с клавиатуры.
